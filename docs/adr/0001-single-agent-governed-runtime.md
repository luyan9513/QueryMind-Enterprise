# ADR-0001：继续采用受治理的单 Agent 运行时

- 状态：Accepted for implementation
- 日期：2026-08-04
- 范围：v0.10 设计与后续实现

## 背景

项目已经有上游 Agent Loop、工具、SQL Governance、Schema Memory 和 RLS，也完成了个人 Query Plan、结构化恢复实验、SQL Reviewer 实验、语义合同、多数据源隔离和评测体系。

v0.6 的真实对照显示，增加一个同模型 SQL Reviewer 后，业务正确率比可比 S3 下降 8.33 个百分点，P95 增加 13.45 秒，成本增加 47.61%。当前主要短板不是缺少第二个 Agent，而是运行状态不可持久恢复、链路不可完整追踪、审批不是可暂停工作流，以及并发和幂等边界不够明确。

## 决策

v0.10 继续使用一个负责意图、规划和工具选择的 Agent，并保留有界工具循环。安全、权限、预算、重复停止和 SQL 放行由确定性组件控制；高风险和业务歧义进入人工审批或澄清。

不在 v0.10 引入多 Agent 编排。优先建设持久化 Run/Step/Event、版本化 API、端到端 Trace、风险审批、幂等和并发控制。

## 备选方案

### 多 Agent：规划、SQL、Reviewer、解释各一个

优点是角色看起来清晰，局部 Prompt 可独立调整。缺点是共享同一错误业务假设、延迟与成本增加、状态与失败组合成倍增长。已有 S4 证据不支持现在采用。

### 完全确定性 Text2SQL Pipeline

更容易测试，但复杂问题需要多次检索、修复和澄清，纯固定流程会失去现有 Agent 的动态工具选择价值。

### 保持现状，只继续调 Prompt/扩题

短期成本最低，但不能回答多用户并发、可恢复审批、端到端审计和线上效果采集等关键工程问题。

## 结果与代价

好处：Agent 范式更容易讲清；复用现有有效能力；把模型自由度限制在适合它的环节；后续评测可以同时看到结果和过程。

代价：需要新增持久化模型和 API；必须处理状态迁移、竞态、数据保存期和脱敏；v0.9 100 题扩展暂缓。

## 重新评估多 Agent 的条件

只有同时满足以下条件才重新评估：

1. 单 Agent 的失败根因能明确归因于上下文/角色冲突，而不是 Schema、口径或治理缺口；
2. 拆分后的组件有独立输入、输出、权限和可离线评分标准；
3. 在冻结测试集上显著改善准确率或安全性；
4. 延迟、成本和故障面仍满足产品预算；
5. A/B 结果可重复，不只依赖 3 题 smoke。

## 归属边界

单 Agent Loop 和基础治理来自上游；本 ADR、v0.10 状态机、API、Trace 和 HITL 方案属于个人设计。实现前不得写成已交付功能。
