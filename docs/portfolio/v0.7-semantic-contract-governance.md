# v0.7 Data-source Semantic Contract Governance

## Outcome

v0.7 adds a data-source-owned semantic contract layer between Schema Memory, Query Plan, and SQL execution. It does not hard-code AdventureWorks rules in the Agent. The generic engine loads a versioned catalog for the active data source; AdventureWorks is one catalog instance used for evaluation.

On the frozen 24-question AdventureWorks benchmark, the final controlled S5 run reached:

- strict accuracy: 58.33% (14/24);
- business accuracy: 66.67% (16/24);
- automatic-answer coverage: 87.50% (21/24);
- business precision among executed answers: 76.19% (16/21);
- wrong-but-executed rate: 20.83% (5/24);
- P50 / P95 Agent latency: 22.11 / 33.92 seconds;
- Schema Recall: 100.00%;
- 20 cases matched and cited at least one contract candidate;
- 23 semantic validation attempts passed and 5 were rejected.

The fair comparison checker reported `comparable=true`. Against the best previous S3 run, S5 added one strict-correct and one business-correct case, reduced wrong execution by one case, kept coverage unchanged, and reduced P50/P95 latency. This is a small measured improvement on one data source, not a universal accuracy guarantee.

## Why this module exists

The v0.6 Reviewer experiment showed that a second model cannot reliably decide whether revenue includes tax, which customer key must be deduplicated, or what time field a metric owns when those definitions do not exist in trusted evidence. v0.7 moves those decisions into auditable data-source configuration.

The runtime flow is:

```text
User question
  -> Schema Retrieve
  -> physical schema evidence + matched semantic candidates
  -> Query Plan cites applicable contract IDs and catalog version
  -> Query Plan evidence validation
  -> SQL-to-plan validation
  -> semantic-contract SQL validation
  -> existing SQL Governance / RLS
  -> database execution
```

The contract layer is not an answer key. It does not contain benchmark filters, expected rows, or reference SQL. It describes reusable business metrics such as revenue, order total, inventory quantity, active employee count, and purchase lead time.

## Catalog shape

Each data source owns one versioned catalog. A metric can declare:

- stable ID, display name, and matching aliases;
- owner and approval status;
- source tables and required physical columns;
- one or more accepted aggregate expressions;
- preferred machine alias and accepted display aliases;
- base grain and default time column;
- mandatory filter columns and explanatory notes.

`config/semantic-contract.example.yaml` is a database-neutral template. `config/semantic_contracts/adventureworks.yaml` is the evaluated AdventureWorks instance.

## Enforcement rules

Three modes are supported:

- `disabled`: no contract prompt or runtime validation;
- `advisory`: calculate issues but do not block SQL;
- `required`: block a cited contract whose formula, table, field, or required filter does not match.

Candidate retrieval and enforcement are intentionally separate:

- matched definitions are candidates, not automatically correct intent labels;
- the Agent cites only the candidate definitions it actually uses;
- a new or uncovered metric continues through the existing schema and SQL governance path instead of being rejected merely because the catalog is incomplete;
- a known matched metric requires a cited, version-bound plan;
- user-facing output aliases are advisory because Chinese labels can vary without changing the metric;
- metric expressions remain hard constraints because changing the formula changes the result.

This distinction came from real failures. The first implementation forced every matched candidate, blocked all unmatched aggregates, and treated preferred output aliases as hard requirements. It reduced coverage without reducing wrong execution. Those rules were replaced with candidate-scoped enforcement.

## Experiment record

### Smoke r2

Two of three questions executed correctly. The category-revenue query was blocked because the plan used `销售收入` while the contract preferred `revenue`. This exposed that output labels are presentation, not metric semantics.

### Smoke r4

After accepting configured display aliases, all three smoke questions passed, with 100% Agent execution and zero wrong execution.

### Full r1

The first 24-question run produced 42.11% business correctness on the old measured-only denominator, 58.33% execution coverage, and 25.00% wrong execution. Root causes were over-strict alias enforcement, requiring all matching candidates, and fail-closing every aggregate not yet covered by the catalog.

### Adaptive smoke r5

An experiment layering contracts onto adaptive Query Plan routing fell to one executed correct answer out of three. Schema retrieval variation caused the Agent to plan too late and run out of useful recovery. S5 therefore retains the stable `always` Query Plan path.

### Final smoke r6 and full r2

Smoke r6 passed 3/3. Full r2 reached the outcome reported above. The final code keeps the generic candidate-scoped rules and the stable plan-first flow.

## Accuracy interpretation

The reporting layer now uses all dataset cases as the denominator for strict and business accuracy. A refusal or unmeasured case counts as incorrect. It separately reports:

- automatic-answer coverage: how many questions were actually executed;
- automatic-answer precision: how many executed answers were correct;
- wrong-but-executed rate: how often the system returned an incorrect executed result.

This prevents a fail-closed strategy from inflating accuracy by removing abstentions from the denominator.

## Remaining failure classes

Eight of 24 cases were not business-correct in the final run:

- three were blocked or exhausted around semantic contracts;
- one violated the evaluator-owned query contract;
- four produced result mismatches involving missing output dimensions, wrong ordering/output shape, or incomplete business joins;
- some SQL passed the metric formula contract but still failed the full question, proving that metric contracts do not validate every join, dimension, ranking, and output-grain decision.

The exact question, reference SQL, Agent SQL, failure location, cause, and recommendation are preserved in the generated `evaluation_detailed.md` and the workspace audit report.

## New data-source onboarding

No AdventureWorks accuracy number transfers to a new database. Before enabling `required` mode for another source:

1. initialize and validate physical Schema Memory;
2. assign a stable `data_source_id`;
3. create a catalog with owners, approval status, formulas, grains, time fields, and filters;
4. create and freeze that source's own benchmark and reference SQL;
5. run disabled/advisory/required comparisons with the same model and snapshot;
6. evaluate all-case accuracy, answer precision, coverage, wrong execution, P95 latency, and confidence intervals;
7. enable required enforcement only for the source and metric coverage that pass admission.

The runtime refuses to load an S5 catalog whose `data_source_id` differs from the active evaluation database.

## Default behavior and limits

Normal chat remains backward compatible: `SEMANTIC_CONTRACT_MODE=disabled` unless explicitly configured. Enabling contracts requires `SEMANTIC_CONTRACT_PATH`.

Current limitations:

- only AdventureWorks has an evaluated catalog;
- keyword candidate matching can still produce overlapping candidates;
- formula checks do not yet express alternative physical implementations or arbitrary conditional aggregates;
- five wrong SQL executions remain in the 24-case run;
- no multi-source admission result, concurrency test, or production SLO exists;
- model pricing was not configured for the final run, so cost is `N/A`.

The next accuracy step is a second data source and a richer contract representation for metric variants, dimensions, join cardinality, and output grain—not another unconstrained LLM Reviewer.
