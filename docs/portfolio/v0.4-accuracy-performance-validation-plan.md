# v0.4 规划：准确率保证、Agent A/B 与跨数据源准入

> 状态：评测框架和首轮 24 题 × 3 模式真实对照已完成；重复稳定性和第二数据源尚未完成。本文中的指标门槛是建议验收标准，不是已经达到的结果。

## 一、核心结论

QueryMind 不能对“任意数据库、任意自然语言问题”承诺 100% 正确。企业可兑现的保证应改成三层：

1. **安全保证**：没有 Schema 证据、违反 SQL Governance 或 RLS 的查询不执行。
2. **范围内准确率保证**：每个数据源在独立冻结题集上达到约定准确率和置信下界后，才开放自动回答。
3. **范围外保护**：业务定义不清、置信度不足或题型未覆盖时，系统澄清、拒答或转人工，不静默猜测。

v0.4 首先验证 Agent 是否比单次 Text2SQL 更值得使用，再决定是否实现快慢双路径。没有 A/B 证据前，不把“Agent 更准确”或“Agent 性能可接受”写成完成成果。

## 二、当前证据与缺口

已完成证据：

- v0.2.1 冻结 24 题：DeepSeek v4 Pro 严格正确率 37.50%，业务等价 54.17%，首次严格 33.33%，平均 Agent 延迟 18.87 秒。
- v0.3 三题真实性冒烟：3/3 最终正确，首次 SQL 正确率 66.67%，平均 Agent 延迟 28.30 秒，P95 36.16 秒。
- Python 正式测试：167 passed，1 个上游 Pydantic 弃用警告。
- 首轮 S0/S1/S2 严格正确率：20.83%/33.33%/50.00%；业务正确率：25.00%/41.67%/54.17%。
- 首轮 S0/S1/S2 P95 延迟：2.65/26.58/53.13 秒；公平性检查通过。

截至 2026-07-29 已补齐：

- `--evaluation-mode s0|s1|s2` 和 `EVAL_MODE` 模式隔离。
- S0 真正执行“一次 Schema 检索、一次模型生成、一次 SQL 尝试”，失败不修复。
- S1 不注册 Query Plan 工具；S2 才启用 Query Plan 门禁。
- checkpoint 和恢复点按模式隔离，报告目录包含模式。
- Wilson 95% 区间、错误但已执行、Recovery Yield、False Block、Plan Acceptance Precision、P50/P95/最大延迟和工具分类计数。
- S0/S1/S2 报告公平性检查及 Markdown/JSON 对比输出。
- 本地正式测试 `167 passed, 1 warning`。

仍缺：

- 多次重复运行后的稳定性和置信区间。
- 第二数据源的独立题集和结果。
- 独立准入集上的自动回答覆盖率、拒答率和错误但高置信回答率。

## 三、A/B/C 实验设计

### 3.1 三个对照版本

| 版本 | 目的 | 运行链路 |
|---|---|---|
| S0 Single-shot | 测“不使用 Agent Loop”的效果 | 固定一次 Schema 检索结果 → 同一模型生成一次 SQL → 只读校验 |
| S1 Agent without Plan | 测上游 Agent Loop、Governance 和恢复本身的价值 | 当前运行时，关闭 Query Plan 必选，保留相同 Schema Retrieval |
| S2 Agent with Plan | 测 v0.3 Query Plan 的增量价值 | 当前运行时，启用证据计划、SQL 对齐和计划恢复 |

S0 不是“把整库 DDL 塞给模型”。当前实现复用同一 Schema Memory 快照、检索模式、limit 和 threshold；S0 用原始业务问题做固定的一次检索，S1/S2 允许 Agent 改写检索和追加检索。这一轮衡量的是完整策略的端到端价值。若要单独归因 Agent Loop，后续还需补一轮“给三组注入完全相同检索结果”的 shared-evidence 实验。

### 3.2 公平性控制

三组必须保持一致：

- 同一冻结题集和同一数据库快照。
- 同一 Agent SQL 模型、Provider、temperature 和最大输出。
- 同一 Schema Memory 数据、Embedding、检索上限和业务描述。
- 同一只读 SQL Runner、结果比较策略和 SQL Contract。
- 同一 Judge 模型；确定性结果一致时仍优先使用完整结果比较。
- 同一并发度。第一轮使用并发 1，减少限流和网络波动。
- 不向任何运行时 Prompt 注入参考 SQL、标准答案或 evaluator contract。

### 3.3 运行规模

第一阶段使用现有 24 题，每个版本独立运行 3 次：

```text
24 题 × 3 版本 × 3 次 = 216 个 Agent/Single-shot 样本
```

即使 temperature 为 0，也保留三次重复，因为云端实现、检索结果和工具路径仍可能波动。

正式执行前记录预计调用量和成本上限；达到用户确认的预算或连续 Provider 故障时停止，不自动扩大实验。

## 四、必须统计的指标

### 4.1 正确性

- 严格完整结果正确率。
- 业务等价正确率。
- SQL Contract 通过率。
- 首次 SQL 严格/业务正确率。
- Schema Recall，以及后续可扩展的字段 Recall。
- 错误但 Agent 实际执行的比例。
- 错误但被判为高置信度的比例。
- 澄清、拒答和无答案比例。

### 4.2 Agent 增量价值

- Recovery Yield：首次错误但最终修复正确的题数。
- False Block Rate：本来正确的 SQL 被计划或 Governance 错误拦截的比例。
- Plan Acceptance Precision：计划通过后最终结果正确的比例。
- 相对 S0 的严格/业务准确率增量。
- 每增加一个正确答案所增加的 Token、费用和秒数。

### 4.3 性能和成本

- 端到端 P50、P95、最大延迟。
- 首 Token 时间；若当前 Trace 不支持，标记为待实现，不能估算。
- LLM 调用次数、Schema Retrieve 次数、Query Plan 次数、run_sql 次数。
- 平均/P95 工具轮数。
- Prompt、Completion、Cache Hit/Miss Token。
- 每题成本、每个正确答案成本和每个最终回答成本。
- Provider 重试、超时和失败次数。

### 4.4 稳定性

- 同一题三次运行结果一致率。
- 从正确变错误或从错误变正确的波动率。
- 每个指标的 95% Wilson 置信区间。
- 24 题只用于回归和方案筛选，不把小样本置信区间写成生产承诺。

## 五、Agent 是否值得使用的决策规则

S2 只有满足下列条件，才可以作为默认路径候选：

1. 严格或业务正确率相对 S0 有明确提升，并且错误执行率不增加。
2. Query Plan 修复的题数大于误拦截的题数。
3. Agent 实际执行成功率没有被 evaluator 事后执行掩盖。
4. P95 延迟和每正确答案成本在约定预算内。
5. 至少两个数据源方向一致，而不是只在 AdventureWorks 有效。

如果 S2 只对复杂题明显更好、简单题延迟明显更差，则不采用全量 Agent，而进入快慢双路径设计：

```text
简单且高置信度 → S0/S1 快速路径
多表、歧义或首次失败 → S2 Agent 路径
证据不足或范围外 → 澄清/拒答
```

路由器属于后续实现，必须先有 A/B 数据；本文不把它写成已完成能力。

## 六、建议性能目标

以下是产品目标，不是当前结果：

| 场景 | 建议目标 |
|---|---:|
| 快速路径 P50 / P95 | ≤8 秒 / ≤15 秒 |
| Agent 路径 P50 / P95 | ≤20 秒 / ≤40 秒 |
| 混合流量整体 P95 | ≤25 秒 |
| SQL 安全违规执行 | 0 |
| Provider 失败有明确错误或降级 | 100% 可观测 |

当前 v0.3 三题平均 28.30 秒、P95 36.16 秒，只接近 Agent 路径 P95 目标，不满足简单问题快速体验。

## 七、跨数据源准确率准入

### 7.1 每个数据源必须独立接入

新数据源不能继承 AdventureWorks 的准确率。接入流程必须包含：

1. Schema 完整性检查：表、字段、主键、外键和数据类型。
2. 业务语义合同：指标公式、粒度、默认时间字段、过滤条件、连接基数和同义词。
3. 参考问题集：开发期 30-50 题，正式准入建议至少 100 题。
4. 参考 SQL 只读执行验证。
5. S0/S1/S2 基线与错误归因。
6. 达到准入门槛后才开启自动回答；否则只开放澄清或人工确认。

### 7.2 题集分层

每个数据源都应覆盖：

- 单表筛选与明细。
- 聚合、分组和排序。
- 时间范围与时间粒度。
- 多表 JOIN 与连接基数。
- 去重、Top N、窗口和同比/环比。
- 空结果、NULL、重复行和边界日期。
- 模糊业务词、超出数据范围和应当澄清的问题。
- 权限、危险 SQL 和元数据探查。

### 7.3 建议准入门槛

以下为待验证的初始门槛，实施前可以调整，但调整必须写入报告：

- 高置信度自动回答的业务等价正确率 ≥90%。
- 95% Wilson 下界 ≥80%。
- 自动回答覆盖率 ≥70%，剩余问题明确澄清或拒答。
- 错误但高置信回答率 ≤5%。
- 无 Schema 证据执行率和安全违规执行率均为 0。
- Agent 实际 SQL 执行成功率 ≥95%。

若样本量不足以支撑置信下界，只能写“试验结果”，不能写“准确率保证”。

## 八、数据源语义合同

为了适配不同数据库，系统需要数据源级配置，而不是 AdventureWorks 硬编码。语义合同至少包括：

```yaml
data_source_id: example
domains: []
metrics:
  - name: revenue
    expression: null
    grain: null
    time_column: null
    required_filters: []
dimensions: []
join_rules: []
synonyms: {}
unsupported_questions: []
reviewed_by: null
reviewed_at: null
```

模型可以建议语义合同，但正式启用前需要数据负责人或题集证据确认。没有业务定义时，系统应澄清，不能从字段名猜公式。

## 九、置信度与拒答怎么做

不能直接相信模型自己输出的“置信度 0.9”。建议使用可审计信号组合：

- 必需表和字段的 Schema 证据是否完整。
- 计划是否命中已审核的指标和 JOIN 规则。
- 是否存在 unresolved question 或业务词多义性。
- SQL 是否一次通过计划、Governance、RLS 和执行。
- 是否发生过 Schema、计划或 SQL 恢复。
- 同一问题的候选 SQL 是否稳定；如果使用多次采样，额外记录成本。

用开发集拟合或选择阈值，用独立准入集报告结果，不能在同一批题上调阈值再宣称准确率。置信门槛最终映射为三种动作：自动回答、向用户澄清、拒答/人工确认。
