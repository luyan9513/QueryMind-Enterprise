# v0.3：Schema 证据计划与可恢复 Text2SQL

## 结论

v0.3 没有重写上游 Agent Loop，而是在现有 `schema_retrieve → run_sql` 链路中加入一个可验证的 Query Plan 阶段，并增强 Schema 精确检索、字段覆盖排序和计划失败恢复。

最终 3 题 DeepSeek v4 Pro 冒烟复测中，严格结果、业务等价、SQL Contract、Schema Recall 和 Agent 内部 SQL 执行成功率均为 100%，首次 SQL 正确率为 66.67%，平均 Agent 延迟为 28.30 秒。该结果只说明三类代表性问题已走通，不能替代 24 题正式评测，也不能外推到其他数据源。

## 能力归属

上游已有：

- Agent Loop、工具注册、Lifecycle Hook 和 Middleware。
- Schema Memory、向量/图混合检索、SQL Governance、RLS 和 `run_sql`。
- Evaluation Runner、LLM Judge、断点续跑和基础报告。

本次个人设计与实现：

- `submit_query_plan` 结构化计划工具。
- Schema 证据累计和计划证据校验。
- `run_sql` 前的计划存在性、表/字段、过滤、输出、聚合、分组、排序和 LIMIT 对齐检查。
- Query Plan 失败后的受限工具恢复和重试上限。
- `table_names + direct` 精确表检索，避免已知表名再次依赖向量排序。
- 必需字段去限定符、精确字段优先、按字段覆盖数重排。
- graph-only 结果回填完整表 Schema；精确检索展示完整字段。
- 对单表主键的无依据 `COUNT(DISTINCT ...)` 做窄范围口径拦截。
- 区分“评测器事后执行成功”和“Agent 内部实际执行成功”的指标修复。

## 运行时链路

```text
用户问题
  → Schema 语义/图检索
  → 已知表名时 direct 精确检索
  → 累计 turn-local 表、字段、主键证据
  → submit_query_plan
      → 证据不足：只开放 schema_retrieve + submit_query_plan
      → 有歧义：停止猜测并请求澄清
      → 计划通过：生成 SQL
  → Registry 对 SQL 和计划做对齐检查
  → SQL Governance / RLS
  → run_sql
```

Query Plan 不读取评测题参考 SQL，也不接收 AdventureWorks 表名白名单。计划只能引用本轮 Schema Memory 真正返回的物理表和字段。

## 为什么没有重写 Agent

真实失败表明，上游循环本身不是首要问题：

1. 模型知道正确表名，但向量检索没有返回该表。
2. 表已召回，但工具只展示前 15 个字段，模型看不到后面的关键日期字段。
3. graph-only 找到表，却没有回填完整字段。
4. 正确 SQL 被计划门禁拦截后，旧评测器会事后执行 SQL，制造表面 100%。

因此本轮改的是“证据、计划、门禁、恢复、评测真实性”五个边界，而不是复制或替换上游 Agent 编排。

## 通用性边界

- 代码没有写死 AdventureWorks 表名、字段名、标准答案或参考 SQL。
- 新数据源仍需重新初始化 Schema Memory、补业务描述、建立独立冻结题集并测 baseline。
- `COUNT(DISTINCT)` 检查只在“单表、无 JOIN、计数列是已召回主键、用户未要求去重”时触发，避免把业务规则泛化成硬编码。
- 3 题结果用于验证恢复链路，不应写成“系统准确率 100%”。正式版本结论必须来自 24 题或更大冻结集。
