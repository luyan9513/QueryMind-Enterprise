# v0.4 实施记录：S0/S1/S2 准确率与性能评测框架

> 更新时间：2026-07-29
> 当前状态：代码、本地测试和首轮 24 题 × S0/S1/S2 真实模型评测已完成。
> 边界：本模块用于测量和比较，不直接提高生产 Agent 的准确率。

## 一、为什么先做这个模块

之前只能看到某次 Agent 评测的准确率，不能回答两个关键问题：

1. Agent 比一次生成 SQL 到底好多少？
2. 多出来的准确率是否值得额外时间、工具调用和模型费用？

因此本轮没有继续增加 Agent 循环，而是先建立可重复、可比较、会主动拒绝不公平实验的评测框架。

## 二、三种模式具体做什么

| 模式 | 运行逻辑 | 用来回答的问题 |
|---|---|---|
| S0 `s0_single_shot` | 原问题检索一次 Schema；调用模型一次；执行 SQL 一次；失败即结束 | 不用 Agent 时的速度和正确率 |
| S1 `s1_agent_without_plan` | 使用上游 Agent Loop、Schema Memory、SQL Governance 和恢复；不提供 Query Plan 工具 | 上游 Agent Loop 本身是否有价值 |
| S2 `s2_agent_with_plan` | 在 S1 上增加个人实现的 Schema Evidence Plan、SQL 对齐和计划恢复 | Query Plan 的增量价值 |

S0 仍通过同一个 `RLSToolRegistry` 执行 SQL，因此只读、RLS、SQL 注入和治理规则没有被绕过。区别只在于它没有 Agent 循环，也不会失败后再试。

## 三、每一步改了什么

### 1. 建立稳定的模式编号

新增 `core/evaluation/mode.py`：

- 接受短写 `s0`、`s1`、`s2`。
- checkpoint 中保存稳定全名，避免后续重命名导致旧结果无法识别。
- 默认保持为 S2，与当前 v0.3 评测行为一致。

### 2. 实现真正的 No-Agent 基线

新增 `core/evaluation/single_shot.py`：

1. 用原始业务问题调用一次 `schema_retrieve`。
2. 把问题和返回的 Schema 证据交给同一个 Agent SQL 模型。
3. 要求模型只返回 `{"sql": "..."}`。
4. 解析出 SQL 后，通过同一个治理 Registry 调用一次 `run_sql`。
5. 无论检索、解析、治理还是执行失败，都直接结束，不进入修复循环。
6. 把 Schema、SQL、成功状态和 Token 记录成与 Agent 相同的 conversation trace，原评测器可以直接复用。

模型看不到参考 SQL、标准结果或 evaluator contract，避免答案泄漏。

### 3. 隔离 S1 和 S2

修改 `EvaluationRuntime`：

- S0 创建 `SingleShotEvaluationAgent`。
- S1 创建上游 `Agent`，但不注册 `submit_query_plan`。
- S2 创建上游 `Agent` 并注册 `submit_query_plan`，同时启用计划门禁。

之前仅把 `require_query_plan=false` 还不够，因为只要工具仍注册，系统 Prompt 就会要求模型先提交计划。本轮把“是否注册工具”和“是否强制门禁”一起隔离。

### 4. 防止恢复点串组

修改 CLI 和 `EvaluationRunStore`：

- 增加 `--evaluation-mode s0|s1|s2` 和 `EVAL_MODE`。
- 新建 checkpoint 时立即写入模式。
- `--resume-latest` 只查找相同模式。
- 显式恢复错误模式时直接报错。
- 报告目录名包含模式，降低覆盖其他组结果的风险。

### 5. 增加可解释指标

新增或补齐：

- 严格正确率和业务正确率的 Wilson 95% 区间。
- P50、P95、最大端到端延迟。
- 各工具调用总数。
- 自动回答覆盖率。
- 错误但实际执行比例。
- Recovery Yield：首个候选错误、最终被 Agent 修对的比例。
- False Block Rate：首个候选业务正确、却被治理或计划门禁挡住的比例。
- Plan Acceptance Precision：计划被接受后，最终业务结果正确的比例。

首次候选正确率和首次实际执行成功率分开保存。这样能识别“SQL 本来是对的，但系统错误拦截”的情况。

### 6. 增加跨运行公平性检查

扩展 `ComparisonReport`，新增 `evals.compare_runs`：

- 对比题目 ID 是否完全一致。
- 对比数据集 hash、数据库/Schema 快照标识、检索预算、方言、Schema 模式、Agent/Judge 模型、Provider、temperature、阈值、并发度等配置。
- 发现差异时仍生成报告，但把 `comparable=false` 写入 JSON，并让命令以失败状态退出。
- 输出每组准确率、延迟、错误执行、工具数、成本，以及相对 S0 每增加一个正确答案所多花的时间和费用。

## 四、怎么运行

建议先做 24 题 × 3 模式 × 1 次，共 72 个样本：

运行前必须给冻结的数据和 Schema Memory 填写同一组人工审计标识；缺少标识时对比器会判为不可公平比较：

```bash
export EVAL_DATABASE_SNAPSHOT_ID=adventureworks_20260729
export EVAL_SCHEMA_SNAPSHOT_ID=adventureworks_schema_20260729
```

```bash
cd /Users/luyan/Documents/Projects/01-QueryMind/repo/QueryMind-personal

EVAL_MODE=s0 .venv/bin/python my_evaluation.py --run-id aw_s0_r1
EVAL_MODE=s1 .venv/bin/python my_evaluation.py --run-id aw_s1_r1
EVAL_MODE=s2 .venv/bin/python my_evaluation.py --run-id aw_s2_r1
```

三组完成后生成对比：

```bash
PYTHONPATH=src .venv/bin/python -m evals.compare_runs \
  --s0-report <S0 evaluation_report.json> \
  --s1-report <S1 evaluation_report.json> \
  --s2-report <S2 evaluation_report.json> \
  --output-dir eval_output/comparisons/adventureworks_r1
```

首轮已经按 S0→S1→S2 执行完毕，公平性检查通过。下一轮是否扩到每组 3 次，应先处理本轮发现的误拦截和高延迟，避免重复消耗模型费用却没有增加有效信息。

## 六、首轮真实结果

三组都使用冻结的 AdventureWorks 24 题、DeepSeek v4 Pro Agent、DeepSeek v4 Flash Judge、temperature=0.0、并发度 1，以及相同的数据库和 Schema 快照。

| 模式 | 严格正确 | 业务正确 | 错误但执行 | 平均 / P95 延迟 | 估算成本 |
|---|---:|---:|---:|---:|---:|
| S0 | 20.83% | 25.00% | 62.50% | 2.01 / 2.65 秒 | $0.023774 |
| S1 | 33.33% | 41.67% | 54.17% | 17.09 / 26.58 秒 | $0.133270 |
| S2 | 50.00% | 54.17% | 41.67% | 29.98 / 53.13 秒 | $0.206584 |

自动对比器判定 `comparable=true`。本轮观察到 Agent 和 Query Plan 的准确率增益，但 S2 仍有 41.67% 错误执行，P95 超过 53 秒，不能作为高可信默认路径。

S2 的 Recovery Yield 只有 8.33%，False Block Rate 为 41.67%，Plan Acceptance Precision 为 56.52%。这说明下一步应该减少错误检索和误拦截、增加风险路由，不应该只增加循环次数。

- `eval_output/comparisons/v0.4-aw24-pro-r1-20260729/evaluation_comparison.md`
- 三组运行目录下的 `evaluation_detailed.md`

## 八、当前实验的限制

三组使用相同 Schema Memory 快照、检索模式、limit 和 threshold，但不是把完全相同的 Schema 文本硬塞给三组：

- S0 固定用原始业务问题检索一次。
- S1/S2 可以让 Agent 改写检索词，并在证据不足时追加检索。

因此当前实验衡量“完整策略是否更好”，包括 Agent 的检索决策价值。若要精确拆出纯 Agent Loop 的因果增益，下一轮需要再做 shared-evidence 对照：提前冻结每题 Schema 结果，并给三组注入同一份证据。

另外，每组当前只运行 1 次，Wilson 区间仍宽且重叠；没有稳定性证据。第二数据源尚未建立，不能复用本轮分数。
