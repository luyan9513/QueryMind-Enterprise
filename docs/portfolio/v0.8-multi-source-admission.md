v0.8 没有把 AdventureWorks 的结果直接外推到新数据库，而是先修复 Schema Memory 多数据源隔离，再为 Chinook 建立独立合同、题集和真实模型准入。

- Neo4j 已完成迁移前备份、显式复合身份迁移和 Chinook 初始化；AdventureWorks 与 Chinook 无跨库关系；
- Chinook 1.0.0 语义目录包含 12 个业务指标；冻结题集包含 24 条中文经营问题；

- S0/S3/S5 r6 使用同一数据集、数据库快照、Schema 快照、模型、温度和并发；公平比较器返回 `issues=[]`；
- S5 达到 66.67% 严格正确率、83.33% 业务正确率、100% Schema Recall、95.83% 自动回答覆盖率和 12.50% 错误执行率；
- 正式 Python 测试为 `213 passed, 1 warning`，`git diff --check` 通过。

按预先定义的 24 题开发门槛，Chinook 当前**通过开发准入**：参考 SQL 100%、Schema Recall 100%、业务正确率 83.33%、覆盖率 95.83%、错误执行率 12.50%、P95 14.39 秒。该结论只允许进入下一阶段扩大评测，不等于生产准确率保证，也不自动切换所有用户请求的默认路由。

这说明 S5 已经在第二数据源上明显优于 S0，但 24 题单次运行仍不能证明“换任意数据都能保持 83.33%”。正式业务保证仍需要至少 100 道分层题、每题多次重复、置信区间和失败降级策略。

## 为什么必须先隔离数据库

上游图身份和 RRF 键原来只使用 `schema.table`。两个数据库若都有 `public.customer`，可能覆盖图节点、跨库扩展或在融合时被当成同一张表。SQL Runtime 连接正确并不能弥补错误 Schema 证据，因此本次先把数据库身份做到存储、检索和融合全链路。

## 迁移安全设计

迁移不会在启动时自动执行。显式入口依次：

1. 检查 Table 是否缺少 `database_name`；
2. 检查新三段键是否重复；
3. 任一检查失败立即停止；
4. 从 `Table-[:HAS_FIELD]->Field` 回填 Field 数据库名；
5. 创建 `(database_name, schema_name, table_name)` 唯一约束；
6. 最后移除旧的二段唯一约束。

实际迁移前已生成 Neo4j dump。过程不清空节点、不删除业务数据库，也不输出连接配置。

S5 相比 S0：

- 业务正确率提高 16.67 个百分点（16/24 → 20/24）；
- 严格正确率提高 16.67 个百分点（12/24 → 16/24）；

## 剩余 4 道业务失败

- `ch_zh_006`：按曲目名称分组，而参考口径按 `track_id` 保留同名不同曲目；属于分组粒度错误。
- `ch_zh_011`：使用内连接，漏掉 0 首曲目的播放列表，也缺少要求的播放列表编号；属于 JOIN 与输出粒度错误。
- `ch_zh_016`：结果本身正确，但 Agent 使用合法 HAVING，题集合同仍要求 WHERE，属于结构合同实现绑定；按当前自动口径仍计失败。
- `ch_zh_024`：用最近两单的 `MAX(date)-MIN(date)` 替代明确的窗口逻辑，且缺少 `invoice_id` 证据；属于时间窗口语义错误。

完整 SQL、错误位置和原因见外层 `reports/audit/v0.8-chinook-evaluation-details.md`；优化过程见 `reports/audit/v0.8-implementation-journal.md`。

## 准入门槛与下一步

开发门槛：参考 SQL 100%、Schema Recall ≥90%、业务正确率不低于 AdventureWorks 同模式或解释差异、错误执行 ≤15%、覆盖率 ≥80%、P95 ≤45 秒。

下一步优先级：

1. 将 Chinook 扩到至少 100 道分层问题，每题至少 3 次，并报告均值、方差、Wilson 区间、P95 和错误分类；
2. 为 JOIN 保留空维度、实体主键粒度、最近两次事件间隔增加数据库无关的计划证据和合同能力；
3. 去除 016 合同对 WHERE/HAVING 具体实现的绑定，并通过新冻结版本复测；
4. 再接第三数据源或第二 SQL 方言，独立建立合同和准入结果。

准确率保证应来自“数据源上线前准入 + 线上抽样回放 + 低置信拒答/澄清”，不是写死某个数据库的 Prompt，也不是承诺 100%。

## r6 日期粒度比较（2026-08-01，已完成）

本轮先处理 `ch_zh_018` 暴露的评测标准化缺口，设计边界如下：

- 在 `ResultComparisonPolicy` 增加显式时间粒度配置；默认保持精确比较，旧数据集结果不变；
- 只有题集明确声明按日期比较时，才把无时区 datetime/timestamp 归一到 `YYYY-MM-DD`；
- 不把非午夜时间、带时区时间或字符串日期自动降级为 date，避免隐藏真实时间语义错误；
- Chinook 018 显式声明日期粒度，因为题面要求“账单日期”，参考 SQL 也明确 `::date`；
- 策略单测、数据集加载和完整测试通过，正式测试为 `213 passed, 1 warning`；
- 全新 r6 S0/S3/S5 已完成且公平检查无差异；018 的 timestamp/date 在业务比较中通过，r5 报告保持不变。
