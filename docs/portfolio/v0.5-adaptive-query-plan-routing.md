# v0.5 自适应 Query Plan 路由：设计、实现与验证

## 结论

v0.5 没有重写 QueryMind 上游 Agent Loop，也没有为 AdventureWorks 写表名或标准答案规则。本轮在现有 Agent 和个人 v0.3 Query Plan 之间增加通用风险路由：

- 简单、单表、证据充分的 SQL 可以直接进入原有 SQL Governance 和 RLS 检查。
- JOIN、子查询、窗口、时间序列、去重、HAVING、集合运算等高风险 SQL 仍必须先提交 Query Plan。
- 正常聊天默认继续使用 `always`，没有仅凭一个数据源的结果把自适应模式设为生产默认。

在相同 AdventureWorks 24 题、相同模型和快照上，S3 两次完整运行的严格正确率均为 54.17%，业务正确率均为 62.50%，错误但实际执行率均为 25.00%。第一次 S3 相比旧 S2 的 P95 延迟从 53.13 秒降到 38.16 秒，平均工具调用从 5.42 降到 4.92；但两次 S3 逐题业务正确性只有 20/24 一致，不能把所有正确率变化都归因给路由器，也不能外推为跨数据源保证。

## 为什么做这次改造

v0.4 的公平对照证明 Agent 在冻结题集上有观察增益，但也暴露两个问题：

1. S2 要求每个问题都提交 Query Plan，简单单表题也承担额外模型轮次。
2. S2 的 False Block Rate 为 41.67%，正确候选可能被计划门禁先挡住。

因此 v0.5 的目标不是继续堆 Prompt，而是让系统按 SQL 结构风险决定是否需要计划，缩短简单题路径，同时保留复杂题的证据门禁。

## 每一步改了什么、为什么改

### 1. 把布尔开关升级为三态模式

涉及：

- `src/QueryMind/core/agent/query_plan.py`
- `src/QueryMind/core/agent/config.py`
- `my_agent.py`

新增 `disabled / always / adaptive`：

- `disabled`：不强制 Query Plan，用于 S1。
- `always`：保持 v0.3/v0.4 S2 行为。
- `adaptive`：由通用风险规则选择快路径或计划路径。

保留 `require_query_plan=True` 的兼容逻辑，旧配置不会静默改变含义。

### 2. 实现数据库无关的 SQL 风险判断

`assess_query_plan_risk()` 只读取以下运行时事实：

- 当前轮 Schema Retrieve 已证明的物理表数量；
- SQL 的通用结构；
- SQL Governance 已提取的形状信息。

只有同时满足以下条件才进入快路径：

- 当前轮恰好有一张被 Schema 证据支持的物理表；
- 只有一个 `SELECT`；
- 没有 JOIN、子查询/CTE、窗口、`DISTINCT`、`HAVING`、集合运算；
- 没有时间序列分桶；
- 没有复杂分组能力。

单表过滤、普通单表聚合和普通分组可以走快路径。规则中没有 AdventureWorks schema、表名、字段名或题号。

### 3. 在真正执行 SQL 前做路由

涉及 `src/QueryMind/rls_registry.py`。

- `always`：没有已接受计划时继续拒绝执行，行为不变。
- `adaptive`：低风险 SQL 记录 `route=fast` 后继续走原有 SQL Governance、RLS 和数据库执行；高风险 SQL 返回 `adaptive_query_plan_required`，要求模型先提交计划。
- 已有计划时仍执行原有 SQL/计划对齐检查。

快路径绕过的只是个人新增的 Query Plan 前置步骤，不绕过上游安全治理。

### 4. 让 Agent 明白两条路径

涉及 `src/QueryMind/core/agent/agent.py`。

自适应模式在运行时追加最终指令：

- 简单单表问题可以检索后直接尝试 SQL。
- 复杂问题必须先提交计划。

运行时指令只解释流程，不注入评测标准答案。

### 5. 修复空 Schema Retrieve 的确定性浪费

真实 S1/S2 Trace 中，模型偶尔调用 `schema_retrieve` 时同时漏掉 `query` 和 `table_names`。v0.5 在调用工具前把原始用户问题回填为检索 query，并记录 `schema_query_fallback_used`。

这不是猜表或补标准答案，只是把 Agent 已经拥有的用户原问题补回必填参数。两次正式 S3 中分别触发 1 次和 0 次。

### 6. 新增 S3 评测模式和路由指标

涉及：

- `src/QueryMind/core/evaluation/mode.py`
- `src/QueryMind/core/evaluation/runtime.py`
- `src/QueryMind/evaluation_cli.py`
- `src/evals/bootstrap.py`
- `src/evals/compare_runs.py`
- `src/QueryMind/core/evaluation/report.py`

新增 `s3_adaptive_agent`，报告记录：

- `query_plan_route_totals`：快路径/计划路径次数；
- `schema_query_fallback_count`；
- S0/S1/S2/S3 公平比较。

### 7. 修复评测中发现的时间序列漏判

第一次 24 题 S3 跑到 11 题时发现 `DATE_TRUNC` 被错误分到快路径。根因是 SQL 已转为大写，但时间序列正则仍按小写匹配。

修复 `sql_governance_shape.py` 为大小写不敏感匹配，并新增回归测试。该次不完整运行保留为失败证据，不参与最终准确率。

## 真实模型评测

固定条件：

- 题集：AdventureWorks 中文经营问题 24 条；
- Agent：DeepSeek v4 Pro；
- Judge：DeepSeek v4 Flash；
- temperature：0；
- 并发：1；
- 数据库快照：`adventureworks_20260729`；
- Schema 快照：`adventureworks_schema_20260729`。

| 指标 | S2 旧基线 | S3 第一次完整运行 | S3 第二次完整运行 |
|---|---:|---:|---:|
| 严格正确率 | 50.00% | 54.17% | 54.17% |
| 业务正确率 | 54.17% | 62.50% | 62.50% |
| 错误但实际执行 | 41.67% | 25.00% | 25.00% |
| 自动回答覆盖率 | 95.83% | 87.50% | 87.50% |
| 平均延迟 | 29.98s | 25.32s | 26.76s |
| P95 延迟 | 53.13s | 38.16s | 43.78s |
| 平均工具数 | 5.42 | 4.92 | 5.04 |
| 估算成本 | $0.206584 | $0.196175 | $0.173933 |
| fast / plan 路由 | 未记录 | 4 / 36 | 3 / 43 |

两次 S3 的总分相同，业务正确性逐题一致率为 20/24（83.33%）。变化题为 `aw_zh_004`、`aw_zh_014`、`aw_zh_017`、`aw_zh_019`，正确与错误发生互换。这说明：

- 可以把快路径命中题的工具和延迟减少视为路由器直接贡献；
- 不能把 S3 比 S2 多出的全部正确题视为路由器因果贡献；
- 还需要至少第二数据源和更多重复运行。

两次 S3 的快路径命中题都业务正确。第一次命中 4 题，第二次命中 3 题；共同命中 `aw_zh_005`、`aw_zh_010`、`aw_zh_022`。

## 为什么没有切换生产默认

`.env.example` 把 `QUERY_PLAN_MODE` 明确写为 `always`。原因不是自适应路由不可用，而是当前证据仍缺：

1. 第二个数据库；
2. 每类问题足够多的分层样本；
3. 多轮稳定性；
4. 对业务语义合同和拒答阈值的正式准入。

新数据源应先使用 `always` 建立基线，再对比 `adaptive`。只有在该数据源同时满足准确率、错误执行率、覆盖率和延迟门槛后，才切换默认。
