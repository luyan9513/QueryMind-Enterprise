# v0.6 Agent 核心改造：结构化失败恢复与 SQL 语义复核实验

## 结论

本轮确实修改了上游 Agent Loop 核心，但正式评测证明：

- 结构化失败分析让恢复过程更可解释、能阻止同类失败无限循环。
- 高风险 SQL 的独立 LLM Reviewer 链路可以运行，但没有提高 24 题整体准确率。
- S4 相比 S3，业务正确率从 62.50% 降到 54.17%，P95 从 38.16 秒升到 51.61 秒，估算成本从 `$0.196175` 升到 `$0.289573`。
- 因此正常聊天默认继续关闭 `structured_failure_recovery` 和 `SQL_REVIEW_MODE`，S4 只作为有证据的实验模式保留。

不能把“修改了 Agent 核心”直接写成“效果已经提升”。本轮最重要的成果是用真实评测否定了一个看起来合理、实际不划算的方案，并把下一步收敛到数据源语义合同。

## 为什么修改 Agent Loop

v0.5 两次 S3 的业务正确率均为 62.50%，但仍存在：

- 税费和运费口径；
- 去重；
- 排序；
- 输出列和别名；
- 条件聚合；
- 失败后重复生成相似 SQL。

Query Plan 可以证明 SQL 与计划一致，却不能证明计划本身理解了业务定义。因此 v0.6 验证两个假设：

1. 结构化失败状态机能否比模型自由恢复更快收敛。
2. 再增加一次独立模型复核，能否发现计划与业务问题之间的语义偏差。

## 上游与个人归属

上游已有：

- Agent Loop 和工具调用；
- 通用异常重试接口；
- Schema Memory、SQL Governance、RLS；
- 基础评测 Runner。

个人本轮修改：

- 在上游 Agent Loop 内加入工具失败分类、失败指纹、动作路由和重复停止。
- 新增 `review_sql_intent` 工具。
- 在 Registry 执行前增加高风险 SQL Reviewer 准入和 SQL 指纹对齐。
- 新增 S4 模式、Reviewer Token/成本计入、Reviewer 与恢复动作指标。
- 修复自适应计划门禁掩盖元数据失败的问题。
- 完成两轮有效 smoke、一次失败 smoke 和一次 24 题正式评测。

## 具体实现

### 1. 结构化失败分析

新增：

- `src/QueryMind/core/agent/failure_recovery.py`

失败被归为：

| 分类 | 恢复动作 |
|---|---|
| 权限、注入、复杂度 | 停止工具并解释 |
| Schema 缺失或元数据探查 | 定向 Schema Retrieve |
| Query Plan 或 SQL 对齐 | 重新计划 |
| Reviewer 未通过或失效 | 修改后重新复核 |
| SQL 执行错误 | 只修复失败结构 |
| 瞬态数据库错误 | 原 SQL 最多重试一次 |
| 未知失败 | 停止并澄清 |

每个失败生成稳定指纹。相同指纹达到 `max_same_failure_retries` 后，工具列表清空，模型只能解释或澄清。

### 2. 元数据失败优先分类

第一次 smoke 中，`information_schema` SQL 被 adaptive Query Plan 提前拒绝，错误阶段显示为 `planning`。模型只要稍微改写 SQL，就会避开旧的元数据失败计数。

修复后：

- 不再依赖 `rejection_stage=governance` 才识别元数据 SQL。
- `information_schema`、`pg_catalog`、常见 `pg_*` 和 `sys` 引用优先归为 Schema Evidence。
- 元数据 SQL 指纹不包含具体 SQL 文本，轻微改写仍算同类失败。

这项修改是数据库无关的，不包含 AdventureWorks 表名。

### 3. 独立 SQL Reviewer

新增：

- `src/QueryMind/core/agent/sql_review.py`
- `src/QueryMind/tools/sql_review.py`

Reviewer 只接收：

- 用户原问题；
- 当前 Schema 证据；
- 已接受 Query Plan；
- 候选 SQL；
- 模型声明的指标、粒度、过滤和假设。

它不接收参考 SQL、评测合同或标准答案。

返回：

- `approve`：允许执行同一条 SQL；
- `revise`：修改计划或 SQL 后重新复核；
- `clarify`：不能自动执行，应向用户澄清。

Registry 使用 SQL 指纹保证 Reviewer 批准的 SQL 与真正执行的 SQL一致。计划或 Schema 更新后，旧 Reviewer 结果失效。

### 4. 工具可见性状态

复杂 SQL 已经接受 Query Plan、但 Reviewer 尚未批准时，下一轮隐藏 `run_sql`，只保留 Reviewer 等必要工具，减少“先执行失败、再被迫复核”。

同一模型仍可能在一次并行工具响应里同时提交计划和 SQL，因此 Registry 还会保留最后一道硬门禁。

### 5. S4 隔离

S4 配置：

- Query Plan：`adaptive`
- Structured Failure Recovery：启用
- SQL Review：`high_risk`

S0–S3 默认不启用新能力，历史对照没有被静默污染。

正常聊天示例默认：

```dotenv
STRUCTURED_FAILURE_RECOVERY=false
SQL_REVIEW_MODE=disabled
```

## Reviewer 为什么失败

S4 有 20 次 Reviewer 调用：

- `approve` 19 次；
- `revise` 1 次；
- `clarify` 0 次。

共有 17 道题实际进入 Reviewer，其中 10 题最终业务正确，7 题最终错误。按题计算，Reviewer 批准后的业务正确率约 58.82%，不足以作为高可信门禁。

Reviewer 批准但仍失败的代表：

- `aw_zh_003`：缺少 `orderqty`；
- `aw_zh_013`：漏掉 `taxamt` 和 `freight`；
- `aw_zh_014`：结果或排序不匹配；
- `aw_zh_016`：缺少 `DISTINCT`；
- `aw_zh_018`：缺少关键字段；
- `aw_zh_023`、`aw_zh_024`：输出别名不符合合同。

唯一 `revise` 出现在 `aw_zh_011`，最终正确，但单个案例不能证明因果提升。

根因：

1. Reviewer 和主 Agent 使用同一模型，容易共享同一个错误假设。
2. Schema 证据描述了表和字段，但没有数据源确认的业务指标定义。
3. “收入”“订单金额”“活跃客户”等术语无法只靠 SQL 结构确定。
4. Reviewer 倾向批准，不能充当准确率保证。

## 当前保留与关闭

保留：

- 失败分类模型；
- 重复失败指纹；
- 元数据失败优先级修复；
- S4 实验模式；
- Reviewer 工具和审计指标；
- 完整负面评测证据。

默认关闭：

- Structured Failure Recovery；
- SQL Reviewer。

原因是当前没有证据证明整套 S4 优于 S3。未来可以单独评测“只启用结构化恢复，不启用 Reviewer”，但不能从本轮结果直接宣称它提高准确率。

## 下一步

下一步不是继续加 Reviewer，而是增加“数据源语义合同”：

1. 为每个数据库建立指标目录，例如收入是否含税费、客户是否去重。
2. 把指标定义、默认时间字段、粒度、允许的 JOIN 关系存入可管理配置。
3. Schema Retrieve 同时召回物理 Schema 和指标合同。
4. Query Plan 必须引用已确认合同；没有合同则澄清。
5. 使用 AdventureWorks 和第二数据源分别评测，不能复用分数。

这能回答当前 Reviewer 无法回答的问题：正确业务口径到底来自哪里。
